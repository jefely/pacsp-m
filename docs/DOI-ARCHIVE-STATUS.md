## 二、`23138538` 中的 DOCX 为什么是错的

**这是整理过程造成的，必须登记。**

### 发生了什么

自动上传脚本在提交文件时：

1. **只按文件名匹配**，未校验内容归属
2. 用 `size` 字段判断是否需重传，而该字段在草稿响应中不可靠
3. **上传后没有下载回验**

结果 DOCX 条目被写入 PDF 的内容。两个文件的 md5 完全相同
（`877b6153211e2fb9c84df9`），大小亦相同（1,518,433），这就是证据。

清理「未完成条目」时，**仓库源码 zip 也被一并删除**。

### 为什么没能在原地修好

Zenodo 的已发布记录文件不可直接编辑，标准路径是 `file_modification` 端点：

```
POST /api/records/23138538/file-modification   → 曾返回 200（files.enabled: true）
                                               → 修复时持续返回 404
POST /api/records/23138538/draft               → 201，但
DELETE/POST .../draft/files                    → 403 "Bucket is locked for modifications."
```

修改资源在每个记录上似为一次性；首次发布后即不可再获取。因此**已发布版本的文件
无法就地更正**，只能新建版本——这正是 `23138930` 的由来。

### 为什么不能删除 `23138538`

Zenodo 不允许删除已发布版本。它保留在版本历史中，永久可见，但**已非最新版本**。

## 六、给后续整理者的教训

本次损坏源于三个可避免的判断失误，均已在 `scripts/pacsp_zenodo.py` 的注释中记录：

1. **把 HTTP 成功当成内容正确。** 上传返回 200/201 只说明请求被接受，
   不说明字节正确。**必须下载回验**。
2. **按名称匹配文件而不校验内容。** 文件名相同不代表内容对应。
   应以哈希为准。
3. **信任响应中的 `size` 字段做控制流判断。** 该字段在中间状态可能缺失或为
   其他文件的值；控制流应基于本地已知的期望值。

由此产生的最重要一条：**任何"修复"脚本都必须在末尾把结果读回来比对**——
第一版修复脚本正因为缺少这一步而报告了成功，实际什么都没修。
