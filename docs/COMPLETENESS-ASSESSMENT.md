## 二、体积：一键引导的硬阻塞

实测依赖占用：

| 包 | 体积 |
|---|---|
| **torch** | **5,409.7 MB** |
| scipy | 111.1 MB |
| transformers | 81.0 MB |
| sklearn | 36.5 MB |
| numpy | 26.1 MB |
| PIL | 14.8 MB |
| 其余 | 18.2 MB |
| **合计** | **5,697.4 MB** |

**可用模型**：

| 模型 | 体积 |
|---|---|
| `bge-small-zh-v1.5` | **91.9 MB** |
| `text2vec-base-chinese` | 390.3 MB |
| `bge-large-zh-v1.5` | 3,726.1 MB |

> **torch 占了 95%。** 而做嵌入推理**不需要完整 torch**——
> `bge` 系列已有 **ONNX** 版本，`onnxruntime` 约 **50 MB**。

**估算**：
```
现状（torch）       5,697 MB + 模型    ≈ 5.7 GB
改 ONNX 后            约 250 MB + 92 MB ≈ 350 MB
```

**改 ONNX 是让"一键引导"可行的前提条件，且是本次评估发现的唯一可解阻塞点。**

〔另需实测〕ONNX 路径必须证明**数值与 torch 一致**——
否则工具与论文的一致性（本项目的既定标准）就断了。

## 三、L4：证明是真的，但从未封顶

**这是本次评估最重要的技术发现。**

`integrity.L4.data.timestamp_proof` 解码实测（840 字节）：

```
魔数          b'\x00OpenTimestamps\x00\x00'          ✅ 正确
日历服务器     4 个真实 btc 日历：
              alice.btc.calendar.opentimestamps.org
              bob.btc.calendar.opentimestamps.org
              btc.calendar.catallaxy.com
              finney.calendar.eternitywall.com
Bitcoin 证明   无
镜像 .ots 文件 存在，840 字节，逐字节相同
```

**所以**：

> **证明是真的提交给了 OpenTimestamps 日历，并拿到了 PendingAttestation。
> 但它从未被 upgrade，因此不含任何 Bitcoin 区块头路径。**

〔这解释了 `pacsp_verify.py` 的 `L4: PEND` 与记录的 `pending_bitcoin_confirmation`〕
**这不是 bug，是未完成的步骤。** 日期是 2026-10-04，至今未 upgrade。

**另一处发现**：`L4.content_hash = 71b1c5f6...`
**不匹配任何 L3 根，也不匹配它们的组合**。
所以**时间戳锚定的哈希无法从记录本身推导**——绑定不透明。
L1/L2/L3 自洽，但 L4 锚的是什么是**外部不可验证的**。

**对"存证性"的含义**：

| 能证明 | 不能证明 |
|---|---|
| 该哈希在 2026-10-04 提交给过日历 | 该哈希对应这条记录 |
| 记录未被篡改（L1/L2/L3） | 某时刻该记录**已存在**于 Bitcoin 上 |

**没有 upgrade，"存证性"只到"我提交过"这一层，到不了"链上可证"。**

## 五、实现理想目标的路径

按"解锁依赖顺序"排列，而非按工作量：

| # | 步骤 | 解锁什么 | 阻塞 |
|---|---|---|---|
| **1** | **切 ONNX 推理** | 一键引导（5.7 GB → ~350 MB） | 需证明数值与 torch 一致 |
| 2 | **升级 L4 并上链** | 真正的存证性 | 需网络 + calendar 可达；可能需 `ots` 客户端 |
| 3 | **自证 L4 绑定** | 记录内可推导时间戳对象 | 需改 `pacsp_build.py` 或文档化该哈希 |
| 4 | GUI 文件选择 + 结果展示 | 用户可用性 | tkinter / 本地 web 界面 |
| 5 | 打包（PyInstaller / 便携 Python） | 一键运行 | 依赖 1 |
| 6 | 工具接存证 | 上传存证 | 依赖 3；需把六层模块并入 PACSP-M |
| 7 | **macOS / Linux 实测** | 跨平台声称 | 需另一台机器 |
| 8 | **外部独立复现** | 验证性声称 | 需第二人 |

**关键判断**：

- **第 1 步是唯一的技术阻塞点**，其余都是工作量或外部条件
- **第 2 步可能不可解**——日历 upgrade 依赖 Bitcoin 确认，而 2026-10-04 的提交至今未确认，
  说明**要么日历没响应，要么从未请求 upgrade**。**需先诊断，不能假定能修好**
- **第 8 步无法由我完成**——需要真实的第二方

## 六、诚实的评估结论

**做得好的**：

1. **科学内核扎实且自证**（183 项核验、与论文逐位一致、九处自我修正有记录）
2. **存证内核真实可用**（9/9 实测通过，篡改 4/4 捕获）——**这一项我原本怀疑，实测证明它成立**
3. **工具把"不该做的解读"编码进输出**——这是超出常规工程的做法

**做得不够的**：

1. **从未有第二人独立复现**——"可验证性"目前只是本机自证
2. **L4 从未上链**——"存证性"只到"提交过"，未到"链上可证"
3. **5.7 GB 体积使一键引导不可行**
4. **无 GUI、无打包、无引导程序**——产品层为零
5. **跨平台从未实测**

**一处方法论上的收获**：

> 本次评估中我**两次差点得出错误结论**——
> 先因传错 `data_dir` 判"存证是假的"（实际 9/9 通过），
> 又需用 Merkle 根反查才确认 `human_poem` 的语料目录。
>
> **验证工具的失败输出，必须先排除"输入用错"，再判定被验证对象。**
> 这与论文 §4.7 的教训同源：**配对/输入的错误会被误读为对象的缺陷。**
